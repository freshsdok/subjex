# Deploy page / 清单页
Evidence opened before designing `GET /deploy`. These are the pages that were read, not a copied console.
- Spring Boot exposes Kubernetes liveness and readiness as `/actuator/health/liveness` and `/actuator/health/readiness`. A probe on a separate management port can succeed even when the main application cannot accept connections. https://docs.spring.io/spring-boot/reference/actuator/endpoints.html
- Liveness and readiness do not depend on each other. A failed readiness probe stops Service traffic and does not by itself restart the container. https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/
- The miss this page is built against: STATUS stays `Running` with zero restarts while READY is `0/1`, because the probe path does not match the route the app serves. The container looks healthy and the Service has dropped it. https://koti.dev/posts/readiness-probe-failure
- Memory quantities are easy to misread. `400m` is 0.4 bytes (millibytes), not 400 mebibytes (`400Mi`). Operators asked the docs to warn that `m` is not mega, because a wrong request is hard to notice. https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/ https://github.com/kubernetes/website/issues/30499
`GET /deploy` is the opposite of that complaint. One sentence says these manifests are not applied to a cluster. Each row is a workload name, the image string from the file (built from that process's Dockerfile, not pushed; mvn test does not build it), the liveness path and the readiness path as separate lines, and the memory limit spelled in mebibytes. The page reads the YAML copied from `deploy/k8s`. There is no cluster status and no apply button.
`GET /deploy` 对着的就是这个抱怨。一句话说明这些清单没有应用到任何集群。每一行是工作负载名、文件里的镜像字符串（由该进程的 Dockerfile 构建，未推送；mvn test 不构建它）、分开写的存活路径和就绪路径，以及用兆比字节写明的内存上限。页面读的是从 `deploy/k8s` 复制来的 YAML。没有集群状态，也没有应用按钮。
